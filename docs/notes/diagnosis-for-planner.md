# 勤務表作成者（A）向けの診断と、LLM 組込の検討メモ

状態: **方向性の議論中（実装なし）。LLM の扱いは、チーム内の議論にはかってから決める。**

## 1. 目的
- 既存の診断（`Diagnosis.explain()`。ID・クラス名・根拠つき）は、導入・運用の担当（B）と開発者（C）向けとして**そのまま残す**。
- それとは別に、**病棟の勤務表作成者（A）向け**に、業務の言葉で「次に何を見直すか」が分かる出力を足したい。

## 2. 現状
- 現行の診断が出すのは、MUS（同時には成り立たない制約の最小の集合）の制約の一覧（ID・クラス名・メッセージ）まで。
- 「N03 さんの 11/07〜11/12 が日勤で固定されています。連続勤務は5日までなので、成り立ちません」のような**原因の文章は、プログラムは作らない**。検討中に出した完成イメージ（手書き）で、制約の組み合わせごとの解釈が要る。

## 3. MUS の性質（A 向けの説明で踏まえること）
- MUS の制約を1つ外せば、**その MUS は解消する**。
- 検出できるのは**1つの MUS**。別の MUS が残っていることがあり、**外しても解が出るとは限らない**。
- 制約を外すのではなく緩和する（上限・下限を変える）場合は、**緩和が不足したり、別の MUS が起きたりしうる**。
- 実例（30人・31日、看護師3を 11/07〜11/13 の7日間、日勤に固定）: 検出した MUS は固定 11/07〜11/12 と連続勤務日数の上限5日。固定を1日外した結果は、11/08〜11/12 では解が出たが、11/07 と 11/13 では出なかった（別の MUS が残る）。上限は 6日では足りず、7日で足りた。

## 4. 水準の整理（LLM を使わない場合 / 使う場合）
| 水準 | 内容 | プログラムだけで |
|---|---|---|
| 事実の列挙 | MUS の制約を、対象（看護師・日付）ごとにまとめて並べる | 作れる |
| 定型の説明 | 制約の種類の組み合わせごとの型（例: 固定割当 + 連続勤務日数の上限）で書く | 型ごとに作る必要がある。組み合わせが増えると保守が重い |
| 一般的な解釈 | 任意の組み合わせについて、原因を自然な文章にする | 難しい（組み合わせを事前にすべて想定できない）。LLM が前提になる |

## 5. LLM を組み込む場合
選択肢（どちらにするかは未決。チーム内で議論する）:
- **クラウドサービス型**: 外部の LLM サービスを呼ぶ。精度は高いが、情報の持ち出しが論点になる。
- **ローカル LLM 型**（自社構築）: 顧客の環境内で動かせる。**精度は不明**で、評価が要る。

| 論点 | 内容 |
|---|---|
| 正しさ | もっともらしい誤りを断定するリスク（ハルシネーション）。MUS の事実だけを渡して、その範囲で説明させる必要がある |
| 情報の持ち出し | 看護師名・勤務の情報を外部に送ることになる。病院の環境によっては禁止される |
| 再現性・検証 | 同じ入力でも出力が変わり、テストしにくい。勤務表は労務管理に関わるので、説明の記録（監査）も論点 |
| 費用・応答時間・オフライン | 呼び出しごとに費用と時間がかかる。ネットワークがない環境では使えない |

## 6. 方向性の選択肢（未決）
- **α**: プログラムだけ。事実の列挙と、制約の種類ごとの見直し先にとどめ、解釈は書かない。決定的でテストでき、誤った断定がない。
- **β**: α を基本に、頻出の型だけ定型の説明を足す。型に合わなければ α に戻る。
- **γ**: LLM による説明を、差し替え可能な任意の部品にする。エンジンは MUS の構造化データ（対象・パラメータ）を出すところまで。説明の生成は外側の層で、LLM か定型かを選ぶ。
- 現時点の見立て（**仮**。未確認）: エンジン側は構造化データを出すところまでとし、説明の水準（α・β・γ）は、利用者と運用が見えてから選ぶ。

## 7. チームで議論したいこと
1. LLM を使うか。使う場合、クラウド型かローカル型か。
2. 顧客の環境で、看護師名・勤務情報の外部送信は許されるか（オンプレミスの要否）。
3. A が診断を読む場面と、必要な説明の水準（事実の列挙で足りるか）。
4. ローカル LLM の場合の精度の評価方法（どの水準を合格とするか）。

## 8. 別課題
- 問題データ（例: `.lp` ファイル）と、ログ・CSV への出力（履歴として残す）。診断の出力とは別に検討する。
