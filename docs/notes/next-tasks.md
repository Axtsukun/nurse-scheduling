## 2. 決まっていること（変えるときはユーザーに確認）
- 求解は CP-SAT、MUS は exact。人数制約の需要は番ごとに一定（基本区間ごとに1制約、統合しない）。
- 制約の名前は ID・クラス名・メッセージ（`docs/design/constraint-message-spec.md`）。
- ブランチは `種別/内容`、`develop` へは PR + squash。

## 3. 未決・未着手の候補（ユーザーが選ぶ）
1. **PR のマージと後片付け**: 上の表のブランチの整理。リリース手順（develop → main）の決定。
2. **実データでの確認**: 実際の病棟データ（勤務・需要・要望）での可解性と診断の読みやすさ。入力の検査（需要は空きなく覆う）が実データに合うか。
3. **72時間ルールの計算単位・期間**: 病棟か届出単位か、原典（告示・通知）で確認（`docs/legal/`）。
4. **MUS の時間制限**: `mus` に時間制限がない（極端な矛盾では戻らない）。扱いを決める。
5. **診断の読みやすさ**: 人数制約は30分の短い区間も出る。まとめ方（例: 同じ番の区間をグループ表示）が必要か、実データで判断。
6. **層3（努力義務・要望）の拡充**: 確度が low の項目は原典を確認してから（`docs/legal/constraints.yaml`）。

## 4. 着手の手順（毎回）
1. `git fetch`・`git status` で現状を確認する。
2. 方針の整理だけを求められたときは、コードを変えず、案（根拠・メリット・デメリット）を示して選んでもらう。
3. 実装は `develop` から `種別/内容` のブランチを切る（他ブランチに依存する場合は伝える）。
4. 変更後は、式の同一性（リファクタリングの場合）、`pytest -q`、`verify.py` で確認する。
