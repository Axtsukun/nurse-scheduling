# 72時間ルールの計算高速化の調査（結論: 採用する対策なし）

調査日: 2026-11-01。結論: **現時点で、理論的な根拠のある有望な対策は見つからなかった**（ユーザーの判断）。
同じ調査を繰り返さないために、試した案・結果・棄却の理由を残す。試作と計測のスクリプトは一時のもので、プロジェクトには含めていない。

## 1. 何が遅いのか
- 72時間ルールを外すと 30人・31日の求解は約0.5秒。有効にすると 3〜19秒（`workers=8`）。night_band を外すと 120秒でも未解決の場合がある。
- **原因は補助変数の数ではなく、ほぼ限界の合計制約そのもの**。
  - 補助変数の定義だけ残して集計の不等式を外すと 0.5秒。上限を3倍に緩めても 1.0〜1.2秒。
  - 規則なしの解でも、算入される26人の平均夜勤時間は 66.8〜70.9 時間で、上限 72 時間に近い。
- 上限を締めるほど急に重くなる（`workers=8`、中央値）: 72時間 約4秒 / 66時間 約20秒 / 62時間 30秒超。58時間は解なしで、約3秒で証明される。

## 2. 試した案と結果（30人・31日・seed 0〜4。各回、独立検証器 `verify.check` で確認）
| 案 | 内容 | 結果 |
|---|---|---|
| V1 | 除外される人の夜勤時間を順序符号化（補助変数 257 → 137 本） | 速くならない |
| V2 | 整数変数で表す（純 PB の方針の外。参考値） | 速くならない |
| V5 | 需要から最低限必要な夜勤時間を LP の双対で求め、含意制約として追加（最小の夜勤時間 3343 単位、スラック約 525 単位） | 速くならない |
| V3 | 規則なしで解いて検証し、違反したときだけ規則を足し、解をヒントにして解き直す | 条件により逆に遅い（62時間の seed0 は時間切れ） |
| V6 | 全員の夜勤時間を 72 時間以下にする十分条件を先に試し、解けなければ現行にもどす | 遅い（約2倍）。66時間以下では解けない場合もある |
| V4 | `workers` を 8 → 4（検証環境のコア数）にする | 中央値で 1.7〜2.4倍速い。**ただし環境依存のため不採用**（下記） |
| V9 | 夜勤時間の合計を最小化する目的関数を足し、最初の解で止める | 条件による。night_band なしでは 2.3倍以上、66時間は約1.5倍、62時間は遅いことが多い、解なし（58時間）の証明が遅くなる（3〜5秒 → 60秒でも未解決）。**不採用** |
| E1 | 夜勤回数の帯の幅 δ（現行 1）を変える | δ=2 は 7.6秒、δ=1 は 4.4秒、δ=0 は 4.3秒。現行が頭打ちの位置 |
| E2 | 個別の夜勤時間の帯を追加（night_band あり） | 4.7秒 → 上限のみ 9.2秒、[48h,72h] 14.6秒。逆効果 |
| E4 | 準夜・深夜の回数を別々に絞る | 4.0秒 → 6.4〜8.1秒。逆効果 |
| E3 | night_band を外し、個別の夜勤時間の帯 [48h,72h] を付ける | 帯なしは 12回中 11回が 90秒で未解決、帯ありは 6回すべて 8〜18秒。**night_band の代わりになる** |

## 3. 判断（ユーザー）
- **`workers` の変更は採用しない**。検証環境（4コア）で `workers=8` はスレッド数がコア数を上回り、並列処理の同期コストで説明できる可能性が高い。汎用的な改善ではない。仮説は直接は検証していない（例: 8コアの環境での比較）。
- **新しい制約を足す案は採用しない**。night_band（個別の夜勤回数の帯 [6,9] 回）が、すでに最適に近い位置にある。係数が揃った「回数」の制約は効くが、係数が 14〜17 とばらつく「時間」の制約は、足すと逆効果。
- night_band を外す運用では、個別の夜勤時間の帯が代わりになる（E3）。ただし運用方針の決定が必要。

## 4. 文献（この規則を直接扱う論文は見つからなかった。2024〜2025年の新しい論文も確認できていない）
- 含意制約が看護師のロスタリングの探索を助けた: [Wong & Chun, 2003](https://unpaywall.org/10.1007%2F3-540-45034-3_72)
- 順序符号化: [Encoding Linear Constraints into SAT](https://arxiv.org/pdf/2005.02073)
- big-M の弱点と直接符号化: [Translating finite-domain integer constraint models … with CPMpy](https://arxiv.org/pdf/2608.15143)（識別子が未来の日付になっており、根拠としては使っていない）
- コストに基づくフィルタリング（縮小費用による枝刈り）: [Focacci, Lodi, Milano 1999](https://www.dcs.gla.ac.uk/~pat/cpM/jchoco/knapsack/papers/focacci99.pdf)、[縮小費用に基づく弧整合の解析](https://arxiv.org/pdf/2207.10325)
- 実行可能性問題に目的関数を足しても、安定して速くなるとは限らない: [No-three-in-line 問題](https://arxiv.org/pdf/2602.07751)
- ヒントとワーカー数の関係: [OR-Tools issue #4166](https://github.com/google/or-tools/issues/4166)

## 5. 限界
- 計測環境は4コア。他のコア数では未確認。
- 規則の余裕は合成データ（夜勤回数の帯 6〜9 回）に依存する。実データでは違う可能性がある。
- 計測は5 seed 以下で、実行ごとのばらつきが大きい。単発の計測で 5〜14倍に見えた効果（V9、62時間）は、seed を増やすと再現しなかった。
- 実データを得たら、規則の余裕（算入者の平均夜勤時間が上限にどれだけ近いか）を最初に確認する。余裕が大きければ、そもそも重くならない。
